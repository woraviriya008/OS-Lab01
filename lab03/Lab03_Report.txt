1. The Race Condition (Phase 2):
In the `race_condition.py` script, what exactly causes the final weight to be less than the expected value? Explain the role of the OS Scheduler in this error.

Answer:
During execution, `race_condition.py` produced an Actual Weight Value of 100 instead of the Expected Weight Value of 200, triggering the "ERROR: Race Condition Detected! Data is corrupted." alert. 
The root cause is that `shared_weight = temp + 1` is not an atomic operation; it consists of three discrete CPU-level instructions:
  1. Reading the shared variable from RAM into local memory (`temp = shared_weight`).
  2. Modifying/incrementing the value (`temp + 1`).
  3. Writing the updated value back to RAM (`shared_weight = temp + 1`).

The OS Scheduler employs preemptive multitasking to allocate CPU time slices. The injection of `time.sleep(0.0000001)` forces the running thread to yield execution, prompting the OS scheduler to perform an immediate context switch before the write-back occurs. Both threads repeatedly read the identical base value from memory before either can commit its increment. Consequently, one thread's update overwrites the other in shared memory, causing exactly 100 update cycles to be lost.

2. Mutex vs. Semaphore (Phase 3):
In `producer_consumer.py`:
- What is the specific job of the `mutex`?
- What is the specific job of the `empty` and `full` semaphores? 
(Why can't we just use a Mutex for everything?)

Answer:
- Job of `mutex`: Enforces Mutual Exclusion. It serves as a binary lock guarding the critical section where the shared `buffer` list and tracking indices (`in_index`, `out_index`) are manipulated. It guarantees that only one thread (Producer or Consumer) can access or modify buffer slots at any single moment, preventing index collisions and data overwrites.
- Job of `empty` and `full` Semaphores: Function as Counting Semaphores and cross-thread signaling mechanisms. `empty` is initialized to BUFFER_SIZE (5) to track available free slots, putting the Producer thread in a blocked/waiting state when the buffer is full (0 available slots). `full` is initialized to 0 to track ready items, putting the Consumer thread in a blocked/waiting state when the buffer is empty (0 ready items).
- Why Mutex Alone is Insufficient: A Mutex only provides binary ownership (locked/unlocked) and mutual exclusion; it has no counter and lacks state awareness. It cannot maintain the count of free or filled slots, nor can it provide condition-based signaling to wake or sleep threads according to buffer boundaries.

3. Deadlock Awareness:
In the Producer function, we wrote:
    empty.acquire()
    mutex.acquire()
What would happen if we swapped these two lines? (mutex first, then empty). Imagine the buffer is completely full. Explain the potential OS problem.

Answer:
If the execution order is reversed to `mutex.acquire()` followed by `empty.acquire()`, and the buffer reaches full capacity (all 5 slots occupied, `empty` count = 0):
1. The Producer successfully acquires the `mutex`, locking the critical section.
2. The Producer calls `empty.acquire()`. Because `empty` is 0, the OS scheduler suspends the Producer into a Blocked state waiting for an empty slot.
3. Critically, the Producer is placed to sleep while STILL HOLDING the `mutex`.
4. The Consumer attempts to run to process an image batch and signal `empty.release()`, but it immediately blocks at `mutex.acquire()` because the locked Mutex is still held by the sleeping Producer.

Both threads are now trapped in a circular wait condition: the Producer waits for the Consumer to signal `empty`, while the Consumer waits for the Producer to release the `mutex`. Neither thread can advance, creating an unrecoverable Deadlock that freezes the application pipeline permanently.
